# Audit-backed reliability metrics — October 16, 2026

[Machine-readable report](metrics.json) and [human-readable summary](SUMMARY.md) calculate engineering success, observed automatic retry frequency, unique transaction rollback frequency, failure-to-validation MTTR, exact workflow latency where available, measured review waits, and stage-level wall durations. The [input manifest](inputs.json) selects seven retained database branches and explicitly labels their provenance. Controlled fixtures and seeded failures have separate cohorts from the three selected live integrated runs. There is no pooled production-reliability estimate.

## Definitions and observed results

Engineering success means the latest observed required engineering validation passed; it does not authorize release. Failure during an unfinished recovery remains unavailable as a final engineering outcome. Observed pass/fail outcomes form the engineering-rate denominator; unknown outcomes are excluded and counted explicitly. The selected live integrated cohort has one passing engineering outcome among three retained runs. These runs were selected from assessment evidence, include assistant-directed interventions, and are neither independent production samples nor a forecast of arbitrary-task reliability.

The integrated thread `e43f07a6-4824-4f49-865f-69ae19899ca1` remains `STOPPED_RELEASE_BLOCKED`: engineering passed, three distinct source transactions rolled back out of four applied (0.75), and zero releases are evidenced. Two automatic retries are observed: the source correction loop and documentation regeneration. The separately human-requested third source generation and the exact-source replay are reported independently. Three implementation model responses remain three responses; replay does not become a fourth generation. Model-response counts are not assumed to be automatic retry counts.

MTTR is the elapsed time from the first engineering failure in an incident to the next passing required engineering validation. Repeated failures before success remain one incident. It includes human/scheduling/idle time and is not advertised as autonomous repair speed. Open incidents are listed and excluded from the mean. The controlled compilation-failure/live-recovery thread has one completed interval of **72.414036 seconds**. The integrated thread's first compilation failure through final combined-test success is **1211.328118 seconds**, including its human-directed intervening work. Source-gate success alone does not end that combined engineering incident. Documentation schema regeneration is a separate retry, outside engineering MTTR.

Latency requires an explicit `WORKFLOW_STARTED` and terminal completion evidence. `WORKFLOW_FINISHED` with an `AWAITING_*` handoff is not terminal completion. Imported-context runs lack an exact start and therefore have null latency, even when terminal. The deliberately failed status-API validation run has a complete **29.458694-second** interval; the other selected branches lack a complete start/terminal pair. Observed first-to-last evidence windows are provided separately and never substituted for end-to-end latency.

Human timing is review-ready audit/checkpoint to recorded decision, including scheduling/resume overhead. It is partial coverage, not a measurement of human thinking time. Matching hashes are checked where both boundaries provide them; requirement changes invalidate old review boundaries. Agent execution uses only explicit matching start/end intervals. Concurrent intervals are unioned rather than summed. Derived source-validation, test-generation, documentation and readiness boundary durations are separately labeled; they are not silently added to measured agent time. Missing requirements/codebase/planning or other stage boundaries remain null with reasons. Unattributed wall time is not classified as agent execution.

Rollback wrapper events are deduplicated by transaction ID. Unidentified rollback/application records make the per-transaction ratio unavailable. Automatic retry counts use known explicit event vocabulary and are labeled observed lower bounds when instrumentation is incomplete. Policy-bound checks compare recorded ordinals with the manifest's supplied three-attempt policy; they do not prove enforcement across unrecorded or manually restarted episodes. Exhaustion means explicit exhaustion evidence or a terminal failed attempt at that bound, not that a successful workflow has spare generation budget.

Release reporting requires matching explicit release authorization/completion evidence; the current application has no such successful release path in these retained runs. A blocked readiness/final-review outcome is never counted as released. This analytics reader adds no approval, deployment, or workflow-resume capability.

The manifest paths refer to the retained `/private/tmp/` evidence databases; supply an equivalent manifest for moved evidence. Paths are opened with SQLite `mode=ro` and `query_only`; output directories must be new. Trusted local checkpoint JSON/msgpack is decoded read-only; pickle checkpoints are rejected. The report is deterministic for a fixed database selection. Branch/thread identity includes the audit database path, so duplicate selection of the same branch/thread is rejected; forked databases remain explicitly separate observations.

Limits include missing stage/request timestamps, partial retry vocabulary, non-monotonic wall clocks, incomplete audit records, caller-supplied provenance labels, and nonsimultaneous snapshots across separate databases. This is retrospective audit interpretation, not cryptographic audit authentication or a complete event-log completeness proof. Release/security/operational sign-offs remain outside this milestone. No production-reliability, released-workflow, or deployment claim follows from controlled assessment fixtures.
