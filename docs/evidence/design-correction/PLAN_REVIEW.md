# Engineering plan review — October 16, 2026

**Recommendation: request changes before implementation.** Structural and declared semantic coverage checks pass, but this plan is not ready to authorize source edits. The workflow remains at the plan-approval interrupt; no approval or execution was submitted. This is a review artifact, not a changed plan or a recorded human implementation decision.

## Findings

1. **High — Approved decisions are not fully delivered to the implementation model.** `implement_task()` validates approval bindings, but constructs its prompt from raw requirement text, the task, source files, and failure diagnostics. It does not include the approved clarification answers, obligation contract, structured plan coverage, or approved design artifact. The raw requirement still contains both unselected and selected expiration alternatives. The task description alone omits the exact UTC, fixed-clock, and equality-boundary specifications. Both the initial generation and targeted-regeneration prompts need the same authoritative approved contract/design context before this plan is executable safely. See [prompt construction](../../../agent-orchestrator/agents/implementation_agent.py#L154).

2. **High — Deterministic time testing has no implementation strategy.** All four test obligations specify `fixed_UTC`, including rejection when expiration equals now. The service calls `Instant.now()` directly in creation and access; the existing tests use wall-clock-independent far-past/far-future constants but cannot control the service's current time. The plan must identify an approved clock seam, preserve Spring construction and existing callers, and specify how tests supply the same fixed UTC instant. Copying `clock: fixed_UTC` into coverage does not implement that seam. Material changes to the architecture should return to design review. See [creation validation](../../../url-shortener/src/main/java/url_shortener/UrlService.java#L42) and [access time](../../../url-shortener/src/main/java/url_shortener/UrlService.java#L78).

3. **High — Test-file authorization currently permits weakening existing tests.** The proposed scope includes `UrlExpirationIntegrationTests.java`. The executor enforces exact edits and file authorization, but “do not weaken tests” is a prompt instruction, not an enforced preservation gate. Before enabling generated-test writes, retain the original tests independently and require them to run unchanged; reject deletion, disabling, reduced assertions, exclusions, or build-configuration changes. Proposed new test files need explicit path/creation authorization, which the current existing-file executor does not support. The next test-generation milestone should establish these protections before treating a green build as proof. See [edit validation](../../../agent-orchestrator/agents/implementation_agent.py#L245).

4. **Medium — The four-file change scope lacks a concrete change rationale.** Optional `Instant expiresAt`, caller forwarding, future-only rejection, persistence, and missing-expiration behavior already exist. The approved design declares no data-model changes and does not list `ShortUrl` as a component, yet the plan includes `ShortUrl.java` and `UrlController.java`. The executor currently requires a real edit to *every* allowed file. This can force gratuitous changes merely to satisfy the proposal validator. Narrow the task to justified changes, or separately review executor support for an authorized subset of files. Preserve HTTP 410 and active redirects with regression tests rather than assuming those paths need modification. See [every-file requirement](../../../agent-orchestrator/agents/implementation_agent.py#L260).

## Required next plan/test-stage work

Define justified per-file changes and the clock seam; propagate the approved design and obligation contract to generation; protect existing tests; and specify assertion-level test cases for future, past, equality, and missing inputs, plus existing HTTP/redirect behavior. Tests should prove that invalid creation does not persist a URL and that accepted expiration round-trips correctly.

Because much of this functionality already exists, a green baseline is expected and cannot demonstrate a new feature. Demonstrate generated-test sensitivity using explicitly labeled, isolated negative fixtures or controlled mutations (for example, remove future-only rejection or allow equality), or select an actually missing approved behavior. The tests must fail for the intended behavioral reason rather than compilation, missing dependencies, or disabled setup. Restore the correct implementation and run both retained original tests and generated tests with real Maven. Do not present deliberate mutation as spontaneously absent functionality.
