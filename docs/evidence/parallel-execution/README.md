## Execution model

The new opt-in LangGraph path runs two to four independently approved, file-disjoint production tasks. Each task receives a separate human interrupt binding its definition to the exact workflow, canonical workspace, requirement version/hash, approved design/contract, plan hash, task definitions, and independent baseline hash. Changes to these bindings stop execution. Existing sequential receipts cannot be adopted as parallel authorization. No new live engineering plan was approved or executed during this milestone.

LangGraph `Send` fans out read-only implementation workers. Each uses the existing implementation executor's authorization, complete-file response validator, and authoritative context, with `prepare_only=True`. Workers cannot apply source changes. They retain prompts, raw responses, diagnostics, outcomes, and task approval receipts. Invalid model output can regenerate within three total attempts per task; authorization, source conflicts, and infrastructure failures stop that worker. A successful sibling is not regenerated because another worker failed.

The LangGraph superstep joins all outcomes before any source application. The coordinator requires exactly one successful outcome per approved task, rechecks all approvals and original bytes, and applies the combined proposal through the existing whole-set source transaction. Task checkpoint mappings identify each task's file checkpoints, shared transaction, and approval receipt. Maven runs only after synchronization and successful application. Original test identities must all execute and pass, with no skips/errors/failures, and the complete protected project inventory is rechecked. Any worker failure prevents all source writes; any combined validation failure compensates the entire production set. Unexpected external source hashes or tampered checkpoints block destructive rollback for review.

This deliberately preserves the transaction manager's one-unfinished-transaction-per-workspace rule. **Model generation and proposal validation run concurrently; filesystem application is coordinated as one transaction.** It does not introduce simultaneous multi-file filesystem visibility or independent concurrent source writers.

## Use and remaining limits

Run the opt-in CLI with `python main.py --design --contract-file CONTRACT_JSON --parallel-evidence NEW_EXTERNAL_DIRECTORY --maven-cache OFFLINE_CACHE`. Requirements, contract, design and engineering-plan gates still precede the new per-task approvals. `--parallel-evidence` cannot be combined with sequential `--plan-lineage` or `--integration-evidence`; the new receipt scheme does not upgrade that adapter. Unsupported plans fail closed. For controlled reproducibility only, run `JAVA_HOME=/path/to/java21 python scripts/parallel_execution_demo.py NEW_DIRECTORY --maven-cache OFFLINE_CACHE` from `agent-orchestrator/`.

This version supports one independent batch, two to four existing-production-file tasks, and no dependency edges, new-file creation, test generation, or test edits. File disjointness and declared dependency absence do not prove semantic independence; human review remains required. Compilation/test failures roll back and stop; only pre-application model-output failures regenerate automatically. Material task/scope/requirement changes require a new reviewed workflow and receipts. Worker completion checkpoints can resume at synchronization without regeneration; abrupt interruption during an uncheckpointed worker or after application but before its graph checkpoint can require manual recovery. Existing durable journals and fail-closed unfinished-transaction detection remain in force; a general automatic crash-recovery scheduler is not provided.

Successful parallel execution returns terminal handoff `AWAITING_PARALLEL_RESULTS_REVIEW`. It does not automatically enter the sequential documentation/readiness adapter or approve test results.
