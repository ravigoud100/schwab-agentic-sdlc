# Compilation failure analysis — October 16, 2026

The analysis replayed the original/generated bytes from all seven retained transaction journals, verified their SHA-256 hashes, read the six bounded-attempt Maven logs, inspected initial/recovery prompts, and checked both original SQLite audit databases. [Machine-readable findings](failure-analysis.json) retain transaction IDs, line references, diagnostics, hashes, and event ordering. The historical evidence has not been overwritten.

## Proven original failure

Every failed proposal used this single-line replacement boundary:

```java
    public UrlService(UrlRepository repository) {
```

Its replacement contained a Clock field, two constructors, and copies of the existing service methods. The executor correctly replaced only that line. The untouched suffix still began with the original constructor assignment and closing brace. In every recorded generated source, line 110 was the orphaned `this.repository = repository;`; `createShortUrl` occurred twice.

All six bounded Maven attempts report the same diagnostic locations:

| Location | Diagnostic |
| --- | --- |
| 110:9 | illegal start of type |
| 110:13 | `';' expected` |
| 110:24 | `<identifier> expected` |
| 113:12 | unnamed classes are a preview feature and are disabled by default |
| 192:1 | class, interface, enum, or record expected |
| 1:1 | unnamed class should not have package declaration |

The latter diagnostics cascade from the malformed class structure. Enabling Java preview features would not repair the source. The recorded logs do not identify missing imports as the original cause.

The proposals also annotated the two-argument repository/Clock constructor with `@Autowired`. The approved design selects the repository-only constructor and explicitly supplies `Clock.systemUTC()` for production. This is an observed design mismatch; compilation failed before a Spring startup failure could be established.

## Generation/recovery defects

The initial prompt mixed a single-line constructor insertion example and recommended constructor-line anchors with a task requiring constructor refactoring. It also warned against that mistake, but the response contract still let the model choose an insufficient boundary. The recovery prompt retained exact-edit mechanics, repeated the failed proposal in multiple sections, and supplied truncated compiler output rather than a clearly separated materialized failing source. The journals demonstrate that the same malformed insertion survived each retry.

The larger-window run evaluated 6,145 prompt tokens on its first call and still produced the error. Its retained metadata and subsequent failures do not establish context-window truncation as the cause. Increasing context or retries is not the fix used here.

Authorization and rollback worked: approval preceded all seven applications, every journal is `rolled_back`, and SQLite records the corresponding restoration events. The underlying exact-replacement executor behaved according to its contract; it did not silently corrupt an otherwise correct replacement.

## Correction

The integrated path now explicitly selects a complete-file response format. The model returns JSON `files` entries with complete Java content. A trusted adapter uses the exact authorized original file as `old_text` and the model's entire content as `new_text`. It supplies no Java implementation itself. This removes model-selected insertion boundaries while retaining existing scope checks, hash checks, checkpoints, transaction application, receipt binding, and rollback.

The complete-file prompt supplies the full original source, imports, approved task, clarification, contract, design (including constructor decisions), plan, and authorization hash. Recovery supplies the materialized failed source and the actual full Maven output separately from the restored original. It does not instruct the model to preserve an insufficient anchor. Legacy exact-edit responses remain available for existing callers; selection is an explicit executor setting, not prompt-keyword detection.

The retry limit remains three attempts. The source gate still requires genuine Maven and every original test before test-generation approval. Test generation, release, and deployment have not been approved by this fix.

## Additional live failure retained

[The first complete-file proposal](complete-file-attempt-1.json) avoided partial insertion and annotated the intended Spring constructor, but omitted the existing `random` and `CHARACTERS` declarations while retaining their uses. Maven reported `cannot find symbol` at 64:25 (`random`), 64:40 and 65:25 (`CHARACTERS`). The workflow rolled it back and automatically forwarded the full sources and diagnostics. This is a new observed generation failure, distinct from the historical constructor-insertion failure; later evidence records its correction outcome.
